type erasure: the beauty and the horror

July 5, 2026

right now only i don't understand type erasure. by the end of this article hopefully both of us will not understand type erasure together.

i think Fedor Pikus described it along the following lines in his Design Patterns book: type erasure is a technique that can be used to separate an interface from an implementation. yeah i wasn't really sure what that meant when i read it either.

basically this is what type erasure gives you: if you have a type erased class whose interface is a subset of some other object's interface, then you can wrap that object with your type erased class. by doing this, you change the object's type to something uniform, this is convenient because you can make objects that were previously different types "of the same type", as long as they both share the common interface. yeah i know it's still confusing

the common example (and the one we will use) is a type erased wrapper for a callable object (ever heard of std::function !). `std::function` is the standard library's implementation of a callable function object. it is also implemented with type erasure. every non-empty std::function object has the ability to be called like a function because it has a call operator (operator()) overloaded. that's why you can assign function pointers, lambdas, functors, or other std::function objects into that type erased class. now you may be wondering why this might be useful? well there's a couple benefits which i will discuss later, but for now i will leave you with this. say you wanted to create a generic container for lambda functions (sounds like a task queue to me!), there isn't really a great way to accomplish this without type erasure. the primary reason being that a lambda's type is both unique and unknown until compile time (when the compiler creates it).

basically type erasure is a technique to achieve runtime polymorphism. the name is kinda misleading too, type erasure doesn't mean that the object loses it's type... everything in C++ needs a type (it is a statically typed language after all...). it's not that the object doesn't have a type, it's that the object's type is hidden behind the implementation of a type erased wrapper class. the new object now becomes something of type "type erased wrapper class". in practice, the original object can either be in a valid but unspecified state (if it was moved into the type erased class), or if it was copied in, then the original object stays in the state it started in.

the last thing i want to mention before i show some code is that, once the type becomes "erased" (hidden by the type erased wrapper), you can't access its facilities that the type erased wrapper doesn't support. if your functor has some other functionality, let's say an accessor method that tracks how many times the functor has been called -- you won't be able to use that facility once the type is erased by std::function (you could via .target<T>() but i'm just gonna pretend that's not there). std::any is another place where type erasure is used, and you actually can get the original type back via std::any_cast, but if you were going to cast it back to the original type you probably want to think about deeply about why you're erasing it in the first place. for context, any time i thought i could use std::any i always immediately realize it doesn't make sense for that situation. but that's my own opinionated take.

okay now that you have some context on what type erasure is and what it can be used for, let's take a look a simplified example: 

// Assume required headers are included.

class CallableObject {
private:
  class Base {
  public:
    virtual ~Base() = default;
    virtual void invoke() = 0;
  };

  template<typename Func>
  class Model final : public Base {
  public:
    Model(Func func) : callable_(std::move(func)) {}

    void invoke() override { callable_(); }

  private:
    Func callable_;
  };

  std::unique_ptr<Base> impl_;

public:
  CallableObject() = delete;

  template<typename Func>
  CallableObject(Func func) : impl_{std::make_unique<Model<Func>>(std::move(func))} {}

  void operator()() {
    impl_->invoke();
  }
};

this is like the most toy model of toy models i can create. i don't want to explain value categories or anything like that so i'm gonna say that this type erased implementation only supports construction via a callable.

okay let me take a stab at explaining this. basically we have a std::unique_ptr to a base class. this should make sense since we want to take advantage of dynamic dispatch. whenever the call operator is used at some call site, the CallableObject runs impl->invoke() which runs the specific invoke implementation that the dynamic type of the object impl_ points to defines. the dynamic type is always going to be some Model<Func> object type, where the Func should have its call operator overloaded (an improved implementation could use concepts to enforce this at compile time).

Okay let's now talk about how we got the Model<Func> object to go inside the the impl_ pointer. obviously std::make_unique is used for creating a unique_ptr, the pointer is of type Model<Func> where Func is the type of the original callable (the type we are erasing). that object (and type) is what's stored (or more accurately hidden) in the Model<Func> object we are creating.

We define our Base class as an abstract class, that defines an invoke() method that Model<Func> must implement. Model<Func> implements it by simply relying on the Func objects operator() implementation.

If you're still confused, I would trace through the code, maybe throw a simple example instantiation in cppinsights.io, and see what template code it generates.

i'm going to mention something really quickly, and if you don't understand it then just forget about it. if you want to learn more Feder Pikus's Hands On Design Patterns book also has a section on it. Okay so basically if you haven't noticed this type erasure stuff requires a heap allocation (in my implementation). and while that can be okay (and is robust), there are plenty of safety and / or performance critical use cases in C++ where this is not desired. Here I'm going to mention you can kind of implement the vtables yourself with small-buffer optimization and inline storage (maybe you've heard of small-string optimization as well -- similar concept). this can help you avoid heap allocations. i've seen code bases where they statically enforce that std::function objects are within a certain size limit so they never allocate. a fun little tidbit of info!

some meta commentary

this technique is mostly used in places where you want polymorphic behavior that doesn't inherit from a common base class, while also being able to use it with an infinite number of types. you can imagine that a lambda that you might write, whose type is opaque until compile time, wouldn't really be able to inherit from a base class (honestly i wouldn't be surprised if it could these days, lambdas have been worked on extensively in each new standard edition).

going back to the container example from before the other technique you could use (other than inheritance discussed above) is using std::variant, which has a lot of benefits (chiefly -- value semantics) but the types have to be known and more importantly compiled together. Therefore std::variant must be used with a closed set of types. type erasure is more generic -- as long as the type fulfills the defined interface, you can larp as the type erased class.

with the edition of concepts you can write really nice type erased classes, since concepts allow you to enforce compile time properties on your template type. so while duck-typing with concepts is its own version of polymorphism, it can also be used very fruitfully in type erased implementations.

alrighty one last thing, i want to mention a couple of places in the standard library where type erasure is used, so you'll actually believe me when I tell you this is useful. i've mentioned std::function and i've also mentioned std::any, but did you know that std::shared_ptr allows a callable deleter to be passed into the smart pointer at construction? it's very elegant because it doesn't add to the smart pointers type information (the deleter object is just stored in the std::shared_ptr's control block), but also provides a very high value feature. you can imagine that on destruction of some object you may not only want to deallocate / destruct the object but maybe you also want to close a file descriptor that was associated with the object. maybe you want to unmap() a shared memory arena when all std::shared_ptr references to it die. type erasure to the rescue! this is different from std::unique_ptr, where the deleter is part of the type, because it's required for knowing the unique_ptr's size. with std::shared_ptr, the deleter is stored in the control block, so the deleter type doesn't appear in the smart pointer's type.

anyway that's a little bit about type erasure.
